# 投稿发布流程优化设计

状态：设计稿，未实施。2026-08-31，Claude Code 撰写。

## 一、当前流程的实际形状

一篇文章从"手里有稿"到"读者能读到"，当前要走完这些：

| # | 环节 | 在哪 | 往返 |
|---|---|---|---|
| 1 | 公众号 PDF 清洗（字形、页眉页脚） | 系统外，手工 | — |
| 2 | 封面压缩/裁切 | 系统外，手工 | — |
| 3 | 作者端 Step1 署名 | AuthorCenter | — |
| 4 | Step2 扉页语 + 内容简介 | AuthorCenter | — |
| 5 | Step3 正文（或上传 DOCX） | AuthorCenter | DOCX 解析 1 次 |
| 6 | Step4 递交 | AuthorCenter | **投稿 1 次（内含 LLM 同步等待）** |
| 7 | 记下回执编号 `BR-{id}-{token}` | AuthorCenter | — |
| 8 | 切到内部工作台（另一套登录） | Studio | 登录 |
| 9 | 刷新待审列表 | Studio | 1 次 |
| 10 | 认领稿件（30 分钟租约） | Studio | 1 次 |
| 11 | 核对五组标签 | Studio | — |
| 12 | 上传封面 | Studio | 1 次 |
| 13 | 审核通过 | Studio | 1 次 |

约 11 次界面交互、6 次网络往返、2 段系统外手工。

## 二、三个瓶颈（均有实证，非推测）

### 1. 投稿请求同步等 LLM —— 唯一的长阻塞

`app/services/author_service.py:173` 在 `submit_article_for_author` 内部同步调用
`extract_tags_for_book(book_id, auto_confirm=False)`。

线上 LLM 配置：`gemini-3.5-flash`，`timeout_seconds=30`，`max_retries=2`。
实测最小提示词往返 **3.1s / 3.1s / 3.2s**；真实打标提示词（系统词 + 标题 + 扉页语 +
简介，输出五组标签 JSON）量级在 5–12s，遇到 429/5xx 重试两次的最坏情况超过 90s。

关键矛盾：**这个标签在提交那一刻没有任何人要看它**。它第一次被使用是编辑打开待审
列表时。把它放在提交请求里，等于让作者替编辑的将来预付一次等待。

### 2. 一人分饰三角，却要跑完整的多人协作仪式

投稿方、审稿方、平台管理员是同一个人，但流程按多人组织设计：认领与租约、必填编辑
意见、回执编号、作者端与编辑端两套登录入口。这些机制在多人场景下都是对的，在当前
的单人场景下是纯开销——第 7～10 步全部属于此类。

### 3. 封面是纯手工链路

`app/services/upload_service.py` 只做校验（MIME 签名、尺寸、5MB 上限），不压缩、不生成
变体。后果已经在生产上发生过：`APPLIED.md` 记录线上曾存在 991KB 与 532KB 的 PNG 封面，
最后由人手工生成 720px JPEG 变体再改库指向。

## 三、设计原则

1. **不删除多人审稿能力**。组织形态可能变，认领/租约/退修/审计都保留原样。
2. **为"一人操作"另开一条直通道**，而不是把主流程改松。
3. **不破坏既有不变量**：`active` 必须伴随 `confirmed` 标签（`publish_invariant` 延迟约束
   触发器）、审计日志、词表校验、service-role-only 的发布 RPC。
4. **优先零新依赖的做法**。

## 四、P0：三件事，收益最大且互相独立

### P0-1 · 把 AI 打标移出提交请求

`submit_article_for_author` 不再同步调用 LLM，改为路由层 `BackgroundTasks` 派发；
返回体里的 `tag_status` 由 `draft`/`unavailable` 扩展出 `pending`。

- 效果：递交从"平均 5–10s、最坏 90s+"变成一次纯数据库写入，**亚秒返回**。
- 编辑端影响：待审列表可能看到"标签生成中"。列表已有 `tags.tag_status` 字段可直接表达；
  `POST /api/books/{id}/extract-tags` 接口已存在，作为"重新生成"入口无需新写。
- 风险：后台任务失败时无人知晓 → 保留现有 `tag_status="unavailable"` 语义，并在编辑端
  把它显示成可点击的"重试生成"。
- 工作量：后端约 20 行 + 测试；前端一个状态标签。

### P0-2 · 单人直发通道（收益最大）

内部工作台新增"新建并发布"：一张表单（标题/作者/扉页语/简介/正文 + 拖入封面），
保存即建稿，后台打标，标签就位后就地展示，操作者扫一眼点"发布"。

后端只需要一个**组合**端点，不需要新的数据库对象：

```
POST /api/editor/articles:publish-direct     (require_review_editor)
body: { title, author, intro, sample, full_content,
        tags?: {五组 + recommend_reason}, cover?: {url, photographer, caption} }
```

内部依次复用已有且已加固的调用：
`create_book`（落 `pending_review` + draft 标签）→ `claim_submission`（本人认领）
→ 若未传 tags 则同步打标一次 → `approve_submission`（走 `publish_reviewed_book` RPC）。

- 为什么安全：全部是既有路径的组合，不新增特权 SQL，发布仍走同一个原子 RPC，
  `claim` 与 `approve` 的审计日志照常写两条。
- 效果：第 3～13 步压缩为"填表 → 拖封面 → 点发布"，约 3 次交互、3～4 次往返，
  且没有任何阻塞等待（标签在后台）。
- 工作量：后端约 60 行 + 测试；前端表单约 200 行（可复用 `staff/editorial.jsx` 的表单原子）。

### P0-3 · 封面在浏览器端压缩后再上传

上传前用 `<canvas>` 把长边压到 1280px、JPEG 质量 0.82 再提交，纯前端、零新依赖。

- 效果：省掉"手工生成 720px 变量"这一段系统外劳动；首页封面加载也随之变快
  （已知：990KB → 62KB 那次手工优化带来的差距）。
- 取舍：重编码为 JPEG 会丢透明通道——封面不需要透明，可接受。
- 备选：服务端用 Pillow 生成变体更规范，但要新增依赖与处理时间，收益相同，故不推荐先做。
- 工作量：前端约 40 行。

## 五、P1：值得做但不紧急

- **标签一键接受**：AI 草稿已在列表里，编辑端默认预勾选并提供"全部接受"，
  把第 11 步从"核对五组"变成"扫一眼点一下"。
- **微信 PDF 清洗内置**：把现有手工配方（字形归一、页眉页脚剔除）做成
  `/api/author/manuscript-text` 的 PDF 分支，消灭第 1 步。需要 `pypdf` 依赖。
- **粘贴即拆分**：整篇粘贴后自动切出标题/扉页语/正文，减少 Step1–3 的重复劳动。

## 六、明确不建议

- **不要**给作者投稿加 `auto_confirm=True` 绕过审核。`book_service.create_book` 的注释
  记着线上出现过 4 篇 `active + draft` 脏数据的教训，`publish_invariant` 就是为此加的。
- **不要**现在就合并作者端与编辑端登录。收益不如 P0-2，改动面却大得多。
- **不要**为了省一次往返把发布逻辑从 `publish_reviewed_book` RPC 里搬出来。

## 七、预期效果

| 指标 | 现状 | P0 全做完 |
|---|---|---|
| 递交请求耗时 | 5–10s，最坏 90s+ | < 1s |
| 界面交互次数 | 约 11 | 约 3 |
| 网络往返 | 6 | 3–4 |
| 系统外手工 | 2 段（PDF、封面） | 1 段（PDF，P1 消灭） |

实施顺序建议 P0-1 → P0-2 → P0-3：先消除阻塞（改动最小、无语义变化），
再压缩步骤（收益最大），最后处理封面（独立、可随时插入）。
